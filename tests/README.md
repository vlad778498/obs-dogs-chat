# Тесты соединения с Twitch IRC

Независимая диагностика проблемы «сообщения перестают появляться через ~60–120 секунд».
Скрипты **не зависят** от `dogs_chat.py` — запускайте их прямо на сервере (OBS-машине),
чтобы проверить, кто виноват: сеть/DNS/фаервол, сам Twitch или код dogs-chat.

## 1. `twitch_connect_test.py` — основной тест (подключение + чтение чата)

Проверяет по шагам: DNS → TCP 6667 (или TLS 443) → регистрация IRC → JOIN канала →
читает реальный чат, шлёт PING каждые 30 c, фиксирует half-open (125 c без байтов).

### Быстрый старт (анонимно, 3 минуты, канал из `/opt/dogs-chat/config/settings.json`)

```bash
cd /opt/dogs-chat && git pull
python3 tests/twitch_connect_test.py
```

### С ключами

```bash
# взять канал и oauth-токен из настроек dogs-chat (по умолчанию путь указан выше)
python3 tests/twitch_connect_test.py --config /opt/dogs-chat/config/settings.json

# или вручную
python3 tests/twitch_connect_test.py --channel mamilokuchii --nick мой_ник --token oauth:xxxxx

# длительнее, например 10 минут (лучше ловит редкие обрывы)
python3 tests/twitch_connect_test.py --duration 600

# через WebSocket 443 вместо TCP 6667 (реализован на чистом Python, pip НЕ нужен)
python3 tests/twitch_connect_test.py --wss
```

### Как читать вывод

| Строка в выводе | Значение |
|---|---|
| `OK: irc.chat.twitch.tv -> ...` | DNS работает |
| `FAIL: порт 6667 блокируется` | фаервол/провайдер режет IRC-порт → используйте `--wss` (443) |
| `msg: user: текст` | PRIVMSG дошёл — канал живой |
| `--- [1 мин] PRIVMSG за минуту: N ...` | поминутная сводка; если N обрывается на 1-й минуте при живом чате — это наш баг |
| `!!! WATCHDOG: 125 c НИ ОДНОГО байта` | реальный half-open: NAT/провайдер уронил путь |
| `ВЫВОД: соединение ЗДОРОВО` | сеть и Twitch ОК — искать проблему в dogs-chat/OBS |
| `ВЫВОД: соединение ЖИВОЕ, но PRIVMSG 0` | в чате тихо ИЛИ проблема в доставке SSE/OBS |

Код выхода: `0` — стабильно весь прогон; `1` — соединение умирало; `2` — не подключиться вовсе.

## 2. `irc_fake_server_test.py` — unit/E2E-тест логики dogs_chat (без интернета)

Прогоняет `TwitchChatThread` из настоящего `dogs_chat.py` против локального
фейкового IRC-сервера, который эмулирует поведение Twitch из логов: пачки PRIVMSG
с неполным «хвостом» пакета, тишина 40+ c, серверные PING. Проверяет, что:
* ложных переподключений НЕТ (`Соединение #1` доживает до конца теста);
* все сообщения приняты;
* watchdog рвёт только при реальном молчании сервера.

```bash
cd /opt/dogs-chat
python3 tests/irc_fake_server_test.py
```

Вывод `E2E PASSED` — логика `dogs_chat.py` здорова; тогда проблемы надо искать
в сети сервера (запустите тест №1) или в канале OBS/SSE.

## Рекомендуемый порядок действий при повторении бага

1. `journalctl -u dogs-chat -f` — смотрите, есть ли `[irc] Watchdog:` и `Соединение #N`.
2. Запустите `tests/twitch_connect_test.py --duration 300` параллельно со стримом.
   * Если тест тоже теряет трафик на ~120 c → проблема сети сервера (NAT/провайдер),
     не кода. Помогает: `--wss` + транспорт ws в settings.json, либо другой DNS/маршрут.
   * Если тест держит связь 5+ минут, а dogs-chat рвёт → пришлите оба лога — это баг кода.
3. `python3 tests/irc_fake_server_test.py` — быстрая самопроверка dogs_chat.py после обновлений.


## ws_opcode_ab_test.py — A/B-доказательство бага «WS 443 мгновенно рвёт»

Проверяет ГИПОТЕЗУ о причине логов вида
`[irc] Соединение потеряно: ConnectionError: WS: сервер закрыл соединение (0 байт)`
через <1 секунду после подключения (логи OBS 02:51):

Twitch закрывает WebSocket, если клиент шлёт IRC-команды **BINARY-кадрами**
(opcode 0x2), и держит соединение при тех же командах как **TEXT** (opcode 0x1).
Старый dogs_chat.py вызывал `conn.send(s.encode())` для всех транспортов; у
WS-клиента `send(bytes)` даёт именно BINARY — отсюда мгновенные смерти только
на WS, тогда как TCP 6667 работал.

```bash
python3 tests/ws_opcode_ab_test.py --seconds 30 [--channel jynxzi]
```

Ожидаемый результат исправленной версии кода (проверено против живого Twitch):
```
[BINARY] строк получено: 0; умерло: ДА через 0.x c
[TEXT]   строк получено: N; умерло: НЕТ — живо все 30 c
ВЫВОД: гипотеза ПОДТВЕРЖДЕНА ...  (код выхода 0)
```

ВАЖНО при самостоятельной доработке теста: NICK обязан уйти ПЕРВЫМ отдельным
WS-кадром (до CAP REQ/JOIN). Если отправить пачку NICK+CAP+JOIN одним кадром,
Twitch отвечает `NOTICE * :Invalid NICK` и рвёт соединение независимо от
опкода — это артефакт теста, а не баг клиента. Между прогонами выдерживайте
паузу 20-60 c: частые handshake с одного IP попадают в rate-limit Twitch,
и TEXT-кейс тоже начнёт умирать (ложный негативный результат).
